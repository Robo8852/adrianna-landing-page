# convex

> **What this covers:** The Convex backend that persists newsletter signups — the `subscribers` table, the `subscribe` mutation, the `ConvexClientProvider` wired into the app shell, the `NewsletterForm` data dependency, env/deploy model, and the (not-yet-built) Resend email seam.

## What
- This is the site's **only backend domain**. Everything else (`primitives` → `composites` → `sections` → `pages`) is static/presentational; this domain is the one place an action leaves the browser and is durably stored. The newsletter signup is the site's single primary CTA, so this is the conversion path made real.
- It does exactly one thing today: **a submitted email is stored, once, in a Convex database**, with a timestamp and a provenance tag. Signups now survive reloads (previously they were discarded — see the history note in `spec/readme.md`).
- It is **serverless / zero-ops** (Convex hosts the DB + functions). The browser talks to it through the first-party `convex/react` client; there is no hand-written API route in `showcase/app`.
- **Out of scope (by design, not omission):** no email is sent (welcome/opt-in/admin) — that is the **Resend phase**, present only as a documented seam (see How). No unsubscribe, segmentation, analytics, admin UI, or rate limiting yet. The Convex dashboard is the only way to read the list.

## Where
- `showcase/convex/schema.ts` — defines the `subscribers` table: `email: string`, `createdAt: number`, `source: string`, with a `by_email` index on `["email"]`. Convex auto-adds `_id` and `_creationTime`; the explicit `createdAt` is kept intentionally so the meaning is ours and survives any re-import.
- `showcase/convex/subscribers.ts` — the `subscribe` **mutation** (the entire backend contract). See How for its behaviour.
- `showcase/convex/_generated/*` — Convex **codegen** (`api`, `server`, `dataModel`). Do **not** hand-edit; regenerated by `npx convex dev`/`deploy`. `NewsletterForm` imports `api` from here via the `@/convex/_generated/api` alias.
- `showcase/convex/README.md`, `showcase/convex/tsconfig.json` — CLI-scaffolded; not load-bearing for this spec.
- `showcase/app/ConvexClientProvider.tsx` — thin `"use client"` provider. Constructs `new ConvexReactClient(process.env.NEXT_PUBLIC_CONVEX_URL!)` **once at module scope** and wraps children in `<ConvexProvider>`.
- `showcase/app/layout.tsx` — **Server Component**; mounts `<ConvexClientProvider>` around `HeaderNav` + `{children}` + `Footer`, so every `NewsletterForm` instance (in `H8` and `Footer`) has the client in context. The layout itself stays server-only — the client lives entirely in the provider.
- `showcase/components/composites/NewsletterForm.tsx` — the sole consumer of the mutation (see `spec/composites.md` for its UX). Calls `useMutation(api.subscribers.subscribe)`.

## How
- **The `subscribe` mutation contract** (`api.subscribers.subscribe`):
  - **Args:** `email: string` (required), `source: string` (optional, defaults to `"unknown"`).
  - **Behaviour, in order:** (1) normalise — `email.trim().toLowerCase()`; (2) validate server-side against the shared regex `EMAIL_RE = /^[^@\s]+@[^@\s]+\.[^@\s]+$/`, and **throw** on failure (server validation is authoritative — the client regex is UX only); (3) **dedup** — look up the normalised email via the `by_email` index and, if it already exists, **return `{ ok: true }` without inserting** (idempotent, silent — re-subscribing is a no-op, never an error, and never discloses "already subscribed"); (4) **insert** `{ email, createdAt: Date.now(), source }` when new; (5) **return `{ ok: true }`** for both new and duplicate (opaque by design — privacy: the caller can't enumerate who is on the list).
  - **Idempotent dedup is the key invariant:** submitting the same email twice yields exactly **one** row and no user-facing error. The `by_email` index makes the lookup O(log n) — never table-scan on submit.
  - **Errors:** only an invalid email throws (generic message). Storage/transport failures propagate as Convex errors; the form turns either into its retry message.
- **`source` values that actually occur in code:** `"h8"` (the H8 primary CTA — `components/sections/H8.tsx`), `"footer"` (the compact footer form — `components/chrome/Footer.tsx`), and `"unknown"` (the prop default, used if a caller omits it). No other placement wires the form today.
- **Client/server split:** `layout.tsx` must remain a Server Component (it owns fonts + metadata). The Convex client is browser-only, so it is isolated in the `"use client"` `ConvexClientProvider`; mounting it around the chrome is what lets the `Footer`'s form reach Convex. This mirrors the split documented in `spec/app-shell.md`.
- **Env vars:**
  - `NEXT_PUBLIC_CONVEX_URL` — the public deployment URL read by the browser client. **Public by design** (it's a deployment URL, not a secret; it grants only what the deployed functions allow, and `subscribe` only writes). Written into `showcase/.env.local` by `npx convex dev` locally; must also be set in **Vercel** for both **Preview and Production**.
  - `CONVEX_DEPLOYMENT` — written by the Convex CLI; used by the CLI only (`dev`/`deploy`), never read by the browser.
  - `.env.local` is git-ignored (root + `showcase/.gitignore`). No secrets are committed.
- **Deploy model:** Convex has its **own** deploy lifecycle, separate from Vercel. `main` auto-deploys the frontend to Vercel production; the backend is pushed with `npx convex deploy` (first cut = **manual**). Production runs against a dedicated prod Convex deployment (distinct from the local `dev` deployment in `.env.local`). Set `NEXT_PUBLIC_CONVEX_URL` in Vercel to the **prod** deployment URL *before* the Convex code reaches `main`, so the first production build that contains the client already has its URL. **Build-time caveat:** because the client is constructed at module scope, `next build` prerender throws *"No address provided to ConvexReactClient"* if the env var is absent — Vercel injects it for real builds, and CI (`.github/workflows/ci.yml`) supplies a placeholder URL for its build smoke test. **Follow-up (not yet done):** wire `npx convex deploy --cmd 'npm run build'` into the Vercel build command so frontend + backend ship atomically; until then the prod deploy is manual.
- **Testing:** `NewsletterForm.test.tsx` **mocks `convex/react`** (`useMutation`) and `@/convex/_generated/api`, so the suite runs with no real deployment. It asserts the mutation is called once with the normalised email + `source`, that an invalid email never calls it, that rejection shows the failure message (not the confirmation), and that controls disable while pending. See `spec/composites.md` §How.
- **Resend seam (NOT built — next phase):** `subscribers.ts` carries a one-line comment marking where a welcome email will be scheduled: `// FUTURE (Resend phase): ctx.scheduler.runAfter(0, internal.emails.sendWelcome, { email })`. Email must live in a Convex **action** (network I/O is disallowed in mutations), so the mutation stays DB-only. The data model is intentionally stable for it — forward fields like `status`, `confirmedAt`, `welcomeEmailSentAt` are anticipated but additive. **When built, `RESEND_API_KEY` belongs in Convex's env (`npx convex env set RESEND_API_KEY … --prod`), NOT in Vercel** — the send happens in the backend, not in Next.js.
