# convex

> **What this covers:** The Convex backend that persists newsletter signups and contact messages — the `subscribers` and `messages` tables, the `subscribe` and `submitContact` mutations, the shared spam-protection stack (honeypot + timing + rate limiter), the `ConvexClientProvider` wired into the app shell, the `NewsletterForm`/`ContactForm` data dependencies, env/deploy model, and the (not-yet-built) Resend email seam.

## What
- This is the site's **only backend domain**. Everything else (`primitives` → `composites` → `sections` → `pages`) is static/presentational; this domain is the one place an action leaves the browser and is durably stored. The newsletter signup is the site's single primary CTA, so this is the conversion path made real.
- It does two things today: **a submitted email is stored, once, in the `subscribers` table** (with a timestamp and a provenance tag); and **a submitted contact message is stored in the `messages` table** (email + message body, optional name, timestamp, provenance). Signups now survive reloads (previously they were discarded — see the history note in `spec/readme.md`).
- It is **serverless / zero-ops** (Convex hosts the DB + functions). The browser talks to it through the first-party `convex/react` client; there is no hand-written API route in `showcase/app`.
- **Both persisting mutations are spam-hardened** by a shared stack: a honeypot field, a submit-timing floor, and the `@convex-dev/rate-limiter` component (six token buckets). Suspicious or rate-limited submissions are **silently dropped** (opaque success) rather than rejected — see How.
- **Out of scope (by design, not omission):** no email is sent (welcome/opt-in/admin notification) — that is the **Resend phase**, present only as a documented seam (see How). No unsubscribe, segmentation, analytics, or admin UI yet. The Convex dashboard is the only way to read the list and the messages.

## Where
- `showcase/convex/schema.ts` — defines two tables. **`subscribers`**: `email: string`, `createdAt: number`, `source: string`, with a `by_email` index on `["email"]`. **`messages`**: `email: string`, `message: string`, `name?: string`, `source: string`, `createdAt: number`, also with a `by_email` index on `["email"]`. Convex auto-adds `_id` and `_creationTime`; the explicit `createdAt` is kept intentionally so the meaning is ours and survives any re-import.
- `showcase/convex/subscribers.ts` — the `subscribe` **mutation** (newsletter contract). See How for its behaviour.
- `showcase/convex/messages.ts` — the `submitContact` **mutation** (contact-form contract). See How.
- `showcase/convex/rateLimits.ts` — shared module exporting the `EMAIL_RE` regex and the `limiter` (`RateLimiter`) instance with all six token buckets. Imported by both mutations so the validation regex and rate-limit policy have a single source of truth.
- `showcase/convex/convex.config.ts` — registers the `@convex-dev/rate-limiter` component via `defineApp()` + `app.use(rateLimiter)`. Required for `limiter` to resolve `components.rateLimiter`.
- `showcase/convex/_generated/*` — Convex **codegen** (`api`, `server`, `dataModel`). Do **not** hand-edit; regenerated by `npx convex dev`/`deploy`. `NewsletterForm` imports `api` from here via the `@/convex/_generated/api` alias.
- `showcase/convex/README.md`, `showcase/convex/tsconfig.json` — CLI-scaffolded; not load-bearing for this spec.
- `showcase/app/ConvexClientProvider.tsx` — thin `"use client"` provider. Constructs `new ConvexReactClient(process.env.NEXT_PUBLIC_CONVEX_URL!)` **once at module scope** and wraps children in `<ConvexProvider>`.
- `showcase/app/layout.tsx` — **Server Component**; mounts `<ConvexClientProvider>` around `HeaderNav` + `{children}` + `Footer`, so every `NewsletterForm` instance (in `H8` and `Footer`) has the client in context. The layout itself stays server-only — the client lives entirely in the provider.
- `showcase/components/composites/NewsletterForm.tsx` — the sole consumer of the mutation (see `spec/composites.md` for its UX). Calls `useMutation(api.subscribers.subscribe)`.

## How
- **The `subscribe` mutation contract** (`api.subscribers.subscribe`):
  - **Args:** `email: string` (required), `source: string` (optional, defaults to `"unknown"`), `hp: string` (optional — honeypot signal), `elapsedMs: number` (optional — submit-timing signal).
  - **Behaviour, in order:** (1) **honeypot** — if `hp` is present and non-empty after trim, **return `{ ok: true }`** (silent drop, no insert); (2) **timing** — if `elapsedMs` is a number `< 1500`, **return `{ ok: true }`** (too-fast = bot, silent drop); (3) normalise — `email.trim().toLowerCase()`, `source ?? "unknown"`; (4) **rate-limit** — check `subscribePerEmail` (keyed on email), `subscribeGlobal`, and `subscribeGlobalHr`; if any bucket is exhausted, **return `{ ok: true }`** (opaque, no insert); (5) validate server-side against the shared regex `EMAIL_RE = /^[^@\s]+@[^@\s]+\.[^@\s]+$/`, and **throw** on failure (server validation is authoritative — the client regex is UX only); (6) **dedup** — look up the normalised email via the `by_email` index and, if it already exists, **return `{ ok: true }` without inserting** (idempotent, silent — re-subscribing is a no-op, never an error, and never discloses "already subscribed"); (7) **insert** `{ email, createdAt: Date.now(), source }` when new; (8) **return `{ ok: true }`** for every reachable path.
  - **Idempotent dedup is the key invariant:** submitting the same email twice yields exactly **one** row and no user-facing error. The `by_email` index makes the lookup O(log n) — never table-scan on submit.
  - **Errors:** only an invalid email throws (generic message). Honeypot/timing/rate-limit rejections never throw — they return the same `{ ok: true }` as success (see opaque-success principle below). Storage/transport failures propagate as Convex errors; the form turns either into its retry message.
- **The `submitContact` mutation contract** (`api.messages.submitContact`):
  - **Args:** `email: string` (required), `message: string` (required), `name: string` (optional), `source: string` (optional, defaults to `"unknown"`), `hp: string` (optional — honeypot), `elapsedMs: number` (optional — timing).
  - **Behaviour, in order:** (1) **honeypot** drop → `{ ok: true }`; (2) **timing** drop (`elapsedMs < 1500`) → `{ ok: true }`; (3) normalise — `email.trim().toLowerCase()`, `message.trim()`, `source ?? "unknown"`; (4) **rate-limit** — `contactPerEmail` (keyed on email), `contactGlobal`, `contactGlobalHr`; exhausted → `{ ok: true }` (opaque, no insert); (5) **validate** — invalid email **throws**, empty `message` **throws** (the only two non-opaque rejects); (6) **insert** `{ email, message, name: args.name?.trim() || undefined, source, createdAt: Date.now() }`; (7) **return `{ ok: true }`**.
  - **No dedup — by design.** Unlike `subscribers`, `messages` does **not** look up `by_email` to suppress duplicates: a person legitimately sends multiple distinct messages over time, so every accepted submission is its own row. The `by_email` index exists for later read paths (e.g. grouping a sender's messages, future Resend notification context), not for write-time dedup.
- **`source` values that actually occur in code:** for **`subscribe`** — `"hero"` (the Hero CTA — `components/sections/Hero.tsx`), `"h8"` (the H8 primary CTA — `components/sections/H8.tsx`), `"footer"` (the compact footer form — `components/chrome/Footer.tsx`), and `"unknown"` (the prop default, used if a caller omits it). For **`submitContact`** — only `"contact-h8"` is currently emitted (the contact form rendered in the H8 section — `components/sections/H8.tsx`), plus `"unknown"` as the default. `"contact-footer"` is **reserved** for a future distinct footer-embedded form; today the Footer "write directly" link merely routes to the H8 form at `/#contact` and captures nothing, so that source string does not yet appear in code.
- **Spam-protection stack (applies to EVERY persisting mutation):**
  - **Honeypot.** Both forms render a hidden field named `company` that real users never fill; the client forwards its value as the `hp` arg. A non-empty `hp` means a bot filled the invisible field, so the mutation silently drops the submission.
  - **Timing floor.** The client measures elapsed time from form render to submit and sends it as `elapsedMs`. Submissions completing in **`< 1500` ms** are treated as bot activity and silently dropped. The check is guarded (`typeof === "number"`) so an absent `elapsedMs` never trips it.
  - **Rate limiter.** The `@convex-dev/rate-limiter` component is registered in `convex.config.ts` and exposed through the shared `limiter` in `rateLimits.ts`. Six **token buckets** (rate per period, with a burst `capacity`):
    - `subscribeGlobal` — 25/min, cap 30
    - `subscribeGlobalHr` — 250/hr, cap 300
    - `subscribePerEmail` — 3 per 10 min, cap 5 (keyed on normalised email)
    - `contactGlobal` — 15/min, cap 20
    - `contactGlobalHr` — 100/hr, cap 120
    - `contactPerEmail` — 3 per 10 min, cap 5 (keyed on normalised email)
    Contact buckets are tighter because it is a lower-volume surface. An exhausted bucket yields opaque success (no insert, no throw).
  - **No per-IP tier (caveat).** Convex mutations cannot observe the client IP, so there is **no per-IP rate limit** — the **global** buckets are the flood defence, and the per-email buckets are the per-actor defence. This is a deliberate limitation of running rate-limiting inside the mutation rather than at an edge.
  - **Parked daily ceiling.** `subscribers.ts` carries a comment-only note for a future `subscribeDaily` bucket (~80–100/day global) to stay under Resend's 100/day free-tier send cap. It is **documentation, not enforcement** — no daily bucket exists yet, and it only matters once the Resend phase actually sends mail.
- **Opaque-success principle:** every rejected or suspicious submission — honeypot filled, too-fast, or rate-limited — returns the **same `{ ok: true }`** as a genuine success: no row is inserted, nothing is thrown, and there is no field, status, or timing difference a caller could use to distinguish a drop from a real save. The only paths that keep a server `throw` are a genuinely **invalid email** (both mutations) and an **empty message** (`submitContact`); these are deterministic input errors the client already guards in its own UX. The canonical handler order is therefore: **honeypot → timing → normalize → rate-limit → validate → dedup (subscribe only) → insert → `{ ok: true }`**.
- **Client/server split:** `layout.tsx` must remain a Server Component (it owns fonts + metadata). The Convex client is browser-only, so it is isolated in the `"use client"` `ConvexClientProvider`; mounting it around the chrome is what lets the `Footer`'s form reach Convex. This mirrors the split documented in `spec/app-shell.md`.
- **Env vars:**
  - `NEXT_PUBLIC_CONVEX_URL` — the public deployment URL read by the browser client. **Public by design** (it's a deployment URL, not a secret; it grants only what the deployed functions allow, and `subscribe` only writes). Written into `showcase/.env.local` by `npx convex dev` locally; must also be set in **Vercel** for both **Preview and Production**.
  - `CONVEX_DEPLOYMENT` — written by the Convex CLI; used by the CLI only (`dev`/`deploy`), never read by the browser.
  - `.env.local` is git-ignored (root + `showcase/.gitignore`). No secrets are committed.
- **Deploy model:** Convex has its **own** deploy lifecycle, separate from Vercel. `main` auto-deploys the frontend to Vercel production; the backend is pushed with `npx convex deploy` (first cut = **manual**). Production runs against a dedicated prod Convex deployment (distinct from the local `dev` deployment in `.env.local`). Set `NEXT_PUBLIC_CONVEX_URL` in Vercel to the **prod** deployment URL *before* the Convex code reaches `main`, so the first production build that contains the client already has its URL. **Build-time caveat:** because the client is constructed at module scope, `next build` prerender throws *"No address provided to ConvexReactClient"* if the env var is absent — Vercel injects it for real builds, and CI (`.github/workflows/ci.yml`) supplies a placeholder URL for its build smoke test. **Follow-up (not yet done):** wire `npx convex deploy --cmd 'npm run build'` into the Vercel build command so frontend + backend ship atomically; until then the prod deploy is manual.
- **Testing:** `NewsletterForm.test.tsx` **mocks `convex/react`** (`useMutation`) and `@/convex/_generated/api`, so the suite runs with no real deployment. It asserts the mutation is called once with the normalised email + `source`, that an invalid email never calls it, that rejection shows the failure message (not the confirmation), and that controls disable while pending. See `spec/composites.md` §How.
- **Resend seam (NOT built — next phase):** both mutations carry a one-line comment marking where mail will be scheduled. `subscribers.ts`: `// FUTURE (Resend phase): ctx.scheduler.runAfter(0, internal.emails.sendWelcome, { email })` (welcome email). `messages.ts`: `// FUTURE (resend-spec): notify Adrianna of new message` (admin notification). The parked `subscribeDaily` ceiling (above) exists specifically to keep total sends under Resend's 100/day free tier once this phase lands. Email must live in a Convex **action** (network I/O is disallowed in mutations), so the mutations stay DB-only. The data model is intentionally stable for it — forward fields like `status`, `confirmedAt`, `welcomeEmailSentAt` are anticipated but additive. **When built, `RESEND_API_KEY` belongs in Convex's env (`npx convex env set RESEND_API_KEY … --prod`), NOT in Vercel** — the send happens in the backend, not in Next.js.
